Architecture Overview

IPRO SDK adopts a clear layered architecture design, providing high modularity and portability for building stable embedded applications. This page covers the system architecture, SoC specifications, build pipeline, and component organization in detail.

System Overview

The overall SDK architecture consists of five main layers, from top to bottom: Application, Components, RTOS, BSP, and Hardware:

Applications (apps/)
bluetooth/ble/ bluetooth/le_audio/ multimedia/ ai/test/ platform/ipro7_demo
Components (components/)
BLE 5.4 LE Audio lwIP mbedTLS CherryUSB Audio AI EVFS LittleFS FatFS Shell LC3
RTOS (FreeRTOS / Zephyr)
FreeRTOS FreeRTOS POSIX OSAL Zephyr v4.4 (module)
BSP (bsp/)
HAL Drivers Board Config Linker Scripts Startup
Hardware (IPRO7)
RISC-V RV32IMAFC BLE Radio NPU

Each layer has clear responsibility boundaries:

  • Application Layer: Self-contained projects, each with its own .config and CMakeLists.txt
  • Component Layer: Reusable middleware, enabled or disabled via Kconfig options
  • RTOS Layer: Task scheduling, synchronization primitives, and timer services; from V2.1.0 the SDK can also be used as a Zephyr v4.4.0 module besides FreeRTOS (see the next section)
  • BSP Layer: Hardware abstraction and drivers, shielding differences between SoC variants
  • Hardware Layer: IPRO series SoC platforms

FreeRTOS and Zephyr

From V2.1.0 the SDK is, besides the FreeRTOS build flow, also a Zephyr v4.4.0 module (zephyr/module.yml); west.yml at the SDK root makes the SDK the west manifest repository. Both paths use the same HAL and SoC drivers; on Zephyr they sit behind Zephyr's device driver API.

Dual-Chip Architecture

IPRO7 has no built-in Wi-Fi. Products requiring Wi-Fi connectivity use a dual-chip architecture: IPRO7 serves as the main SoC, handling application logic, AI/NPU inference, BLE, audio, and peripheral control, while Wi-Fi connectivity is provided by an external SDIO Wi-Fi companion. V2.1.0 provides an ATBM6162 SDIO module probe (ipro_atbm_probe), the SDIO host Wi-Fi reference application ipro7_sdio_wifi, and the host side for the IPRO6S FIN card on the IPRO7AI Reef EVK (the defconfig_wifi_ipro6s build of ipro7ai_reef_demo).

Dual-Chip Connectivity Architecture

Application logic / AI & NPU / BLE
Audio / ISP / peripheral control
SDIO
SDIO Wi-Fi (connectivity companion)
Wi-Fi

Tip: IPRO7 itself integrates an EMAC Ethernet MAC, so wired Ethernet networking with lwIP works without a companion chip (see the ipro7_demo reference application; for ENC28J60 over SPI see ipro_enc28j60_test). The IPRO6S-side firmware for the FIN card is not included in V2.1.0; contact INTELPRO. The IPRO6S radio application ipro6_if_wifi is only in V2.0.1.

OCRAM 256 KB 0x11010000 High-speed SRAM Stack, interrupt handlers, performance-critical code
HBNRAM 4 KB 0x20090000 Hibernate Retention Critical data preserved during deep sleep

Configuration System (Kconfig)

The SDK uses a Linux kernel-style Kconfig system for project configuration. Each application has its own .config file, and the build automatically generates build/include/generated/autoconf.h for use in C code.

Configuration Hierarchy

  1. Option definitions: Root Kconfig and per-component Kconfig files - define all available options
  2. Project defaults: apps/<project>/defconfig - project default configuration, loaded via make defconfig
  3. Actual build configuration: apps/<project>/.config - application-specific configuration (highest priority)
defconfig Workflow 
cd apps/bluetooth/ble/ipro_ble_remote

# Generate .config from the project defconfig
make defconfig

# After editing .config, save the minimized configuration back to defconfig
make savedefconfig

Key Configuration Options

.config Example 
# SoC selection
CONFIG_IPRO7=y
CONFIG_CPU_ID="intelpro_ipro7"

# RTOS selection
CONFIG_FREERTOS_SUPPORT=y

# Wireless features
CONFIG_BLUETOOTH_LE_ENABLE=y

# Component enables
CONFIG_COMPONENTS_LWIP_ENABLE=y
CONFIG_COMPONENTS_MBEDTLS_ENABLE=y

# Test auto-run
CONFIG_TEST_AUTO_RUN=y

Configuration to Code Relationship

build/include/generated/autoconf.h (auto-generated) 
/* Auto-generated by Kconfig, do not edit manually */
#define CONFIG_IPRO7 1
#define CONFIG_CPU_ID "intelpro_ipro7"
#define CONFIG_FREERTOS_SUPPORT 1
#define CONFIG_BLUETOOTH_LE_ENABLE 1
#define CONFIG_COMPONENTS_LWIP_ENABLE 1
Tip: CONFIG_CPU_ID must be correctly set in .config for cmake/toolchain.cmake to detect the proper architecture flags. The toolchain detection logic automatically distinguishes between vendor GCC (with _xxldsp DSP extension instructions) and standard GCC, adapting compiler flags accordingly.

Application Structure

Each application is a self-contained directory under apps/, containing all files needed for building and configuration:

Typical Application Structure 
apps/<category>/<project>/
├── .config              # Kconfig configuration (generated from defconfig via make defconfig)
├── defconfig            # Project default configuration
├── Kconfig              # Project-specific Kconfig options
├── Makefile             # Make build entry point
├── CMakeLists.txt       # CMake build definition
├── main.c               # Application entry point
├── src/                 # Source code directory
├── include/             # Header files directory
└── build/               # Build output (auto-generated)
    ├── include/
    │   └── generated/
    │       └── autoconf.h   # C header generated from .config
    └── build_out/
        └── <project>_IPRO7.bin  # Final binary

Minimal main.c Skeleton

All FreeRTOS applications share the components/os/freertos/freertos_app_hooks.{c,h} component. The heap, FreeRTOS hooks (idle/tick/stack-overflow/malloc-failed), and assert handler are all provided as weak-symbol defaults, so an application's main.c does not need to repeat this boilerplate:

Minimal main.c 
#include "freertos_app_hooks.h"
#include <FreeRTOS.h>
#include <task.h>

static void app_task(void *arg)
{
    /* Application main logic */
    for (;;) {
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    ipro_platform_init();   /* heap + boot2 + log + shell initialization */
    xTaskCreate(app_task, "app", 1024, NULL, 5, NULL);
    vTaskStartScheduler();
    while (1) {}
}
Tip: To customize a hook (e.g., vApplicationIdleHook), simply define a non-weak version with the same name in your application source. The linker picks it up automatically — no changes to the shared component are needed.

BLE Stack

The Zephyr 4.4 host runs on the FreeRTOS port and communicates with the RivieraWaves v14.0.2 controller through an in-memory HCI byte stream.

components/wireless/bluetooth/
├── ipro_bt_host/
│   ├── upstream/zephyr/include/zephyr/bluetooth/
│   ├── upstream/zephyr/subsys/bluetooth/
│   ├── port/
│   └── tinycrypt/
├── ipro_ble_controller/
│   ├── include/
│   ├── lib/
│   └── CMakeLists.txt
└── ble_common.cmake
LIBACLRoles
link1_periph1Peripheral
link11Central + Peripheral
link22Central + Peripheral
link44Central + Peripheral

Choose CONFIG_IPRO_BLE_CTLR_FEATURE="bt52" for basic BLE or "bt54_iso2" for BLE 5.4 with two ISO streams (CIS/BIS). The latter requires CONFIG_EM_SIZE of at least 32 KB. Keep the host connection limit within controller capacity; preserve the shipped PDM link2 / CONFIG_BT_CONN=1 configuration.

Host sources are included. The V2.1.0 controller package contains 16 IPRO7 archives (link1_periph / link1 / link2 / link4 × bt52 / bt54_iso2 × debug / release); configuration selects the variant. The 6 IPRO6S BR/EDR archives are only in V2.0.1. When building with Zephyr RTOS, the Zephyr host uses the same prebuilt IPRO7 controller archives.

BSP & Drivers

The Board Support Package is located in bsp/, providing hardware abstraction and peripheral drivers:

  • bsp/hal/ - Hardware Abstraction Layer API
  • bsp/hal/lp_framework/ - Low-power framework (PDS/HBN sleep mode management, provided as a prebuilt library)
  • bsp/drivers/ - Peripheral drivers
  • bsp/board/ - Board configuration (pin mapping, clock settings)
  • bsp/common/ - Startup code, linker scripts, shared code

Tools & Debugging

V2.1.0 includes the build CLI, Kconfig helper scripts, Linux x86-64 CMake, the serial monitor tools/serial_monitor.py, the OTA packer tools/create_ota.py, the Zephyr tools tools/zephyr/ and Android demo source. The flash tool, board-test script, crash parser and OpenOCD configurations are separate.

The IPRO SDK provides an integrated toolchain covering the complete development cycle: build, flash, monitor, and debug.

Online Installer 3.4.0 reads the component catalog; the fixed 3.3.0 installer bundles SDK 1.2.1. As of the V2.1.0 release (2026-10-15), the catalog still lists SDK 1.2.1 as stable. Obtain V2.1.0 from its GitHub Release and select its extracted directory explicitly. Installation and version selection

Unified Build CLI (build_freertos.sh)

./build_freertos.sh lives at the SDK root and is the unified development entry point bundled with the Release SDK. Multiple actions can be chained in a single command and are executed in order.

Command Format 
./build_freertos.sh [actions...] [options] <project>

Actions

Action Description
build Build the project (default when no action is given)
clean Clean the build directory
flash Flash the binary to the board
monitor Open the serial monitor
size Show ELF size and memory region usage
test Build + flash + monitor, waiting for the auto-test result pattern

Options

Option Description Default
-p, --port PORT Serial device path (used by flash / monitor / test) Set per your actual device (e.g. /dev/cu.usbserial-XXXX)
-t, --timeout SEC Timeout in seconds for monitor / test 30
-w, --wait-for PAT Regex pattern the monitor waits for -
-d, --defconfig FILE Use an alternate defconfig (build output goes to build_<name>/) -
-j, --jobs N Number of parallel build jobs -
-v, --verbose Show full build output -
-l, --list List all available projects -
-h, --help Show help -

Common Examples

Unified CLI Examples 
# List all available projects
./build_freertos.sh -l

# Build (default action)
./build_freertos.sh platform/ipro7_demo

# Clean, then rebuild
./build_freertos.sh clean build platform/ipro7_demo

# Build → flash → monitor (full development cycle)
./build_freertos.sh build flash monitor bluetooth/ble/ipro_ble_remote

# Show ELF size and memory region usage
./build_freertos.sh size platform/ipro7_demo
flash and test need the separately obtained IntelProCube command-line tool (set IPRO_FLASH_TOOL or put the tool directory on PATH). monitor and test use the bundled tools/serial_monitor.py: they open the -p port at 115200 baud, send reboot first and stop after -t seconds. For a console at another baud rate, run serial_monitor.py directly with --baud.

Flash Tool

⚠️ The IntelProCube v0.6.3 command-line tool (ipro_iot_tool.exe, ipro_iot_tool_macos, ipro_iot_tool_linux) is not included in IPRO SDK V2.1.0; obtain it from INTELPRO. ./build_freertos.sh flash <project> uses the tool named by IPRO_FLASH_TOOL, or the tool for your host on PATH.

The IPRO SDK uses the IntelProCube command-line tool to flash compiled firmware to the development board's Flash memory.

Basic Usage

Flash Firmware 
# Run from the IntelProCube directory (ipro_iot_tool_linux on Linux, ipro_iot_tool.exe on Windows)
# Adjust the serial port path to match your actual device
./ipro_iot_tool_macos --chipname ipro7 --chip-variant IPRO7 \
    --port /dev/cu.usbserial-XXXX \
    --baudrate 921600 \
    --firmware <SDK>/apps/bluetooth/ble/ipro_ble_remote/build/build_out/ipro_ble_remote_IPRO7.bin

# IPRO7AI Reef EVK (2 MB flash)
./ipro_iot_tool_macos --chipname ipro7 --chip-variant IPRO7AI \
    --port /dev/cu.usbserial-XXXX \
    --baudrate 921600 \
    --pt chips/ipro7/partition/partition_cfg_2M.toml \
    --firmware <SDK>/apps/platform/ipro7ai_reef_demo/build/build_out/ipro7ai_reef_demo_IPRO7.bin

Parameters

Parameter Description Example
--chipname Target chip model ipro7
--chip-variant Flash pin configuration of the board: IPRO7 (flash pin 0x2) or IPRO7AI (0x9, IPRO7AI EVK / Reef EVK) IPRO7
--port Serial device path /dev/cu.usbserial-XXXX (macOS, depends on your device)
/dev/ttyUSB0 (Linux)
--firmware Firmware binary path apps/.../build/build_out/*.bin
--baudrate Flash transfer baud rate 921600
--pt Partition table; the IPRO7AI Reef EVK uses the 2 MB table chips/ipro7/partition/partition_cfg_2M.toml
⚠️ The tool has no --flash-pin option and exits 0 even when flashing fails; check its output for [All Success] (./build_freertos.sh flash does this for you). build_freertos.sh calls the tool without --chip-variant and --pt; for the IPRO7AI EVK and Reef EVK run the tool directly with --chip-variant IPRO7AI, or adjust the flash pin in the tool's configuration file as the application README describes.

Entering Download Mode

The board must be in download mode before flashing. ./build_freertos.sh flash first sends reboot_dl through tools/serial_monitor.py at 115200 baud. If the console runs at another baud rate or the firmware has no shell, send the command yourself or use the BOOT pin as the board guide describes:

Enter Download Mode 
# Firmware with a 115200-baud console
python3 tools/serial_monitor.py /dev/cu.usbserial-XXXX --send reboot_dl --timeout 2

# Firmware with a 921600-baud console (macOS)
python3 tools/serial_monitor.py /dev/cu.usbserial-XXXX --baud 921600 --send reboot_dl --timeout 2
⚠️ On macOS, you must use /dev/cu.* device paths. Do not use /dev/tty.* as it will block indefinitely waiting for the DCD signal.

Serial Monitoring

V2.1.0 includes tools/serial_monitor.py. It opens the port with the Python standard-library termios module (no pyserial needed), can send one command, wait for a regular-expression pattern and save the output to a file. It runs on macOS and Linux; on Windows use the extension's IPRO: Serial Monitor or another serial terminal.

Serial Monitor Examples 
# Monitor for 60 seconds (115200 baud by default)
python3 tools/serial_monitor.py /dev/cu.usbserial-XXXX --timeout 60

# Send reboot and wait for the test result
python3 tools/serial_monitor.py /dev/cu.usbserial-XXXX --send reboot \
    --wait-for "ALL TESTS PASSED|SOME TESTS FAILED" --timeout 30

# 921600 baud with a log file (macOS)
python3 tools/serial_monitor.py /dev/cu.usbserial-XXXX --baud 921600 --timeout 60 --log console.log
Option Description Default
--baudBaud rate115200
--timeoutSeconds to monitor30
--sendCommand sent before monitoring (for example reboot, reboot_dl)-
--wait-forRegular-expression pattern; stop when it matches-
--logSave the raw output to a file-

Exit codes: 0 when a pattern containing PASSED matches, 1 for any other match, 2 on timeout, 3 if the port cannot be opened.

Console Baud Rates

The console baud rate of a FreeRTOS application is set per application by CONFIG_PLATFORM_UART_BAUDRATE, default 115200; the IPRO7AI Reef EVK console is on connector U6. These applications use 921600: ipro7ai_evk_demo, ipro7ai_evk_launcher, ipro7ai_evk_rps, ipro_meeting_poc, ipro7_uvc_cam, ipro_epd_el036. Zephyr images (ipro7_evb, ipro7ai_evk) use UART0 at 2,000,000 baud.

On hosts other than macOS, serial_monitor.py supports rates up to 230400 only; use another serial terminal for 921600 or 2,000,000 baud. On macOS use /dev/cu.*. Stop monitoring before flashing to release the port.

Zephyr Tools (tools/zephyr)

Since V2.1.0 the SDK is also a Zephyr v4.4.0 module, supporting ipro7_evb (IPRO7 EVB) and ipro7ai_evk (IPRO7AI EVK). tools/zephyr/ provides the scripts below; see Zephyr RTOS for the full guide.

Script Purpose
bootstrap.shCreates the west workspace in zephyr-workspace/: downloads Zephyr v4.4.0 and the modules listed in west.yml and applies zephyr/patches.yml; -w DIR sets the location, IPRO_TOOLCHAIN the toolchain path
build.shBuilds a Zephyr application: -b ipro7_evb (default) or ipro7ai_evk, -p pristine, -d build directory; the application is a path or a sample name under zephyr/samples/
flash.shFlashes zephyr.bin (--build-dir or a .bin path, --port) with the IntelProCube command-line tool, sending reboot_dl through serial_monitor.py first
monitor.shOpens the UART0 console at 2,000,000 baud (--port, --baud, --timeout)
ci_build.shBuilds the sample matrix (pristine, warnings as errors) and prints image sizes; select ipro7_evb or ipro7ai_evk with -b, -q builds only hello_world and blinky
Zephyr Quick Start 
tools/zephyr/bootstrap.sh          # west workspace in zephyr-workspace/
source zephyr-workspace/env.sh     # ZEPHYR_BASE, CROSS_COMPILE, west
cd zephyr-workspace
west build -b ipro7_evb zephyr/samples/hello_world
west build -b ipro7_evb ../zephyr/samples/periph_smoke -d build/smoke
west flash                         # IntelProCube command-line tool: $IPRO_FLASH_TOOL or on PATH

The first bootstrap.sh run downloads Zephyr and its modules from GitHub and needs Python 3.10+, CMake 3.20 or later, Ninja, git, dtc and the IPRO RISC-V toolchain (/opt/toolchain/riscv_ipro7).

west flash enters download mode through the IPRO7 CMSIS-DAP probe by default; without one, use west flash -- --boot shell (the running image's reboot_dl) or --boot manual. Select the port with --port or $IPRO_SERIAL_PORT; otherwise the only USB serial port present is used. The Zephyr console is UART0 at 2,000,000 baud, unlike the FreeRTOS applications; open it for a given number of seconds with tools/zephyr/monitor.sh --port /dev/cu.usbserial-XXXX --timeout 60.

On-board Tests

The SDK includes apps/test/ipro_unit_test/ for HAL and shared-component tests. Build it, flash the matching board with the separate flash tool, then inspect the console for ALL TESTS PASSED or SOME TESTS FAILED.

make -C apps/test/ipro_unit_test

tools/board_test.sh is not bundled. ./build_freertos.sh test ipro_unit_test builds, flashes (with the separately obtained IntelProCube command-line tool), sends reboot and waits for the result above; it exits 0 on pass, 1 on failure and 2 on timeout (-t sets the seconds, default 30).

The AI, ISP, RF, LC3 and low-power framework libraries in this package are prebuilt .a archives without source code. They can be linked, but source-level stepping inside them is unavailable.

GDB Debugging

⚠️ The OpenOCD configurations (tools/openocd/) are not included in IPRO SDK V2.1.0 — contact INTELPRO to obtain them.

The IPRO SDK supports JTAG debugging through OpenOCD + GDB. The IPRO7 JTAG pins are GPIO0 (TMS), GPIO1 (TDI), GPIO2 (TCK), and GPIO9 (TDO).

Start OpenOCD

Start OpenOCD Server 
# Use the SDK-provided OpenOCD configuration
# (generic RISC-V JTAG setup, valid for both IPRO6 and IPRO7)
openocd -f tools/openocd/openocd_ipro6.cfg

# On success it prints:
# >>> Ready for GDB on port 12021

Connect GDB

Launch GDB and Connect 
# Use the SDK toolchain's GDB
/opt/toolchain/riscv_ipro7/bin/riscv64-unknown-elf-gdb \
    apps/platform/ipro7_demo/build/build_out/ipro7_demo_IPRO7.elf

# Inside GDB, connect to OpenOCD
# (the port is set by gdb_port in the config file, default 12021)
(gdb) target remote :12021
(gdb) monitor reset halt
⚠️ The configuration files define no flash bank, so load inside GDB cannot program the XIP Flash (0x13000000). Use the flash tool to program firmware; GDB is for breakpoints, single-stepping, and memory inspection.

Common GDB Commands

Command Description
b main Set breakpoint at main function
b file.c:42 Set breakpoint at a specific file and line
c Continue execution
s / n Step into / Step over
p variable Print variable value
x/16xw 0x11010000 Examine memory (16 words in hex)
bt Show backtrace / call stack
info reg Display register state

Crash Analysis

⚠️ parse_backtrace.py is not included in IPRO SDK V2.1.0 — contact INTELPRO to obtain it. Even without this tool, you can resolve addresses manually with the toolchain's built-in addr2line (see below).

When the firmware encounters an exception, the exception handler outputs the exception PC, SP (with its owning stack range), saved s0(fp) / ra, and a stack dump. parse_backtrace.py converts these addresses into source file names and line numbers.

Usage

Parse from File 
# Parse crash log from a file
python3 tools/parse_backtrace.py \
    /opt/toolchain/riscv_ipro7/bin/riscv64-unknown-elf- \
    apps/platform/ipro7_demo/build/build_out/ipro7_demo_IPRO7.elf \
    backtrace.txt
Parse from Pipe / Stdin 
# Pipe from clipboard or file
cat backtrace.txt | python3 tools/parse_backtrace.py \
    /opt/toolchain/riscv_ipro7/bin/riscv64-unknown-elf- \
    apps/platform/ipro7_demo/build/build_out/ipro7_demo_IPRO7.elf

Parameters

Parameter Description
toolchain_prefix Toolchain prefix path (including trailing -)
elf_file Corresponding ELF file (with debug symbols)
backtrace_file Crash log file (optional, reads from stdin if omitted)

Manual Analysis (addr2line)

Any address in the exception output that falls within a code region (e.g. Flash starting at 0x13000000) can be resolved to a function name and source location with the toolchain's built-in addr2line:

Manual addr2line Resolution 
# Resolve a single address to a function name and source location
/opt/toolchain/riscv_ipro7/bin/riscv64-unknown-elf-addr2line \
    -e apps/platform/ipro7_demo/build/build_out/ipro7_demo_IPRO7.elf \
    -f -C 0x1301c148
💡 Parsing requires the ELF file (.elf) with debug symbols, not the .bin file used for flashing. ELF files are located in the build/build_out/ directory.

Build Size Analysis

Use ./build_freertos.sh size <project> (bundled with IPRO SDK V2.1.0) to inspect firmware memory usage and understand how much Flash and RAM the firmware consumes.

Usage

Memory Size Analysis 
# Show ELF size and per-section usage (run 'build' first)
./build_freertos.sh size platform/ipro7_demo

The output includes an overall size summary and a per-section breakdown:

  • text - Code section (stored in Flash)
  • data - Initialized data (occupies both Flash and RAM)
  • bss - Uninitialized data (occupies RAM only)
  • Size and address of each section (e.g. .text, .data, .bss)

IPRO7 Memory Layout

Region Size Base Address
Flash Board-dependent (e.g. 2 MB on the IPRO7AI Reef EVK) 0x13000000
PSRAM 8 MB 0x1e000000
OCRAM 256 KB 0x11010000
HBNRAM 4 KB 0x20090000

OTA Packaging (create_ota.py)

tools/create_ota.py packs a combined firmware image into the boot2 OTA format. The input must be the combined image with its boot header, such as chips/ipro7/img_create_iot/whole_img.bin produced by the IntelProCube command-line tool, not the .bin from the SDK build; the script stops if the input has the wrong format.

Create an OTA Package 
# XZ-compressed by default, writes whole_img.xz.ota
python3 tools/create_ota.py <IntelProCube>/chips/ipro7/img_create_iot/whole_img.bin

# Uncompressed, with an explicit output file
python3 tools/create_ota.py whole_img.bin --raw -o firmware.ota

--fw-ver sets the firmware version string written to the OTA header.

macOS Development Notes

There are several platform-specific considerations when developing on macOS.

Serial Ports

⚠️ On macOS, always use /dev/cu.* instead of /dev/tty.*. The tty.* devices wait for the DCD (Data Carrier Detect) signal, causing programs to block indefinitely.
Operating System Serial Device Path
macOS /dev/cu.usbserial-XXXX (depends on your device)
Linux /dev/ttyUSB0

Bundled CMake

V2.1.0 includes a Linux x86-64 CMake under tools/cmake/; it is not a macOS executable. Install CMake 3.19+ for macOS (for example, brew install cmake) and put it on PATH. project.build prefers system CMake on POSIX hosts.

Common Issues and Solutions

Issue Cause Solution
Serial program hangs Using /dev/tty.* Switch to /dev/cu.*
Incomplete cat output macOS buffering issues Use tools/serial_monitor.py, an external serial terminal or the extension monitor
"Resource busy" error stty -f holding the port Close the holding process; use Python approach
CMake won't run cmake (PATH) is a Linux x86-64 ELF Use brew install cmake

Recommended Serial Port Flags

Python Serial Port Example 
import os

# Correct way to open serial ports on macOS (path depends on your device)
fd = os.open("/dev/cu.usbserial-XXXX", os.O_RDWR | os.O_NOCTTY | os.O_NONBLOCK)

Development Workflow

./build_freertos.sh -l
./build_freertos.sh clean build ipro_ble_remote
./build_freertos.sh size ipro_ble_remote

After building, flash with the separately obtained IntelProCube command-line tool (or ./build_freertos.sh flash) and inspect the serial output with tools/serial_monitor.py or a terminal. For Zephyr applications use west and tools/zephyr/ instead. In VS Code use IPRO: Build, IPRO: Flash and IPRO: Serial Monitor after verifying the active SDK and tool paths.

For HAL regression checks, build ipro_unit_test and follow the on-board test instructions above. Record the SDK version, board configuration and actual hardware result.

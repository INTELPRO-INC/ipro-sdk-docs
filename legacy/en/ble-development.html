BLE Development Guide

This guide covers BLE application development with the IPRO SDK's Bluetooth stack. The SDK uses the Zephyr BLE Host Stack paired with a RivieraWaves prebuilt controller, with features determined by the selected controller profile.

Zephyr BLE Host Architecture

IPRO SDK FreeRTOS applications use the Zephyr BLE Host as their BLE host stack: components/wireless/bluetooth/ipro_bt_host/ is ported from the Zephyr BLE Host (GAP, GATT, L2CAP, SMP, ISO, LE Audio) and runs on top of FreeRTOS via the port/ layer. Applications always develop against the Zephyr-style bt_* APIs. V2.1.0 also supports the full Zephyr RTOS (v4.4.0): Zephyr applications use Zephyr's Bluetooth host on the same IPRO BLE prebuilt controllers; see Zephyr RTOS. The rest of this page focuses on FreeRTOS applications.

  • Host — Zephyr 4.4 source: ipro_bt_host/ is ported from Zephyr; full source ships with the SDK and can be read and debugged directly
  • Controller: ipro_ble_controller/lib/ — 16 IPRO7 prebuilt archives; see the configuration matrix below. V2.1.0 includes no IPRO6S controller archives.
  • RTOS: in FreeRTOS applications, scheduling, queues and timers come from FreeRTOS and the host uses FreeRTOS through the port/ layer; Zephyr RTOS applications use the Zephyr kernel directly
Further reading: the complete BLE Host Architecture Guide is not included in the release package — contact INTELPRO to obtain it.

Stack Architecture

The BLE stack uses a Host + Controller dual-layer architecture, communicating through on-chip HCI (no UART HCI transport):

Application Layer
GAP / GATT Services / Profiles
BLE Host (Zephyr 4.4)
GAP / GATT / L2CAP / SMP / ISO
HCI (On-Chip)
ipro_ble_ctlr_hcitl
BLE Controller (RivieraWaves)
Link Layer / PHY (1M/2M/Coded)

Core Concepts

  • Zephyr BLE Host: The Zephyr BLE Host Stack is used even on FreeRTOS. Applications interact through the standard bt_* APIs
  • RivieraWaves Controller: Provided as prebuilt static libraries, handling Link Layer and PHY management
  • On-Chip HCI: Host and Controller communicate via on-chip HCI, no UART HCI transport layer required
  • Callback-driven: All asynchronous events (connection, disconnection, notifications) are handled through callback functions

IPRO6S BLE + BR/EDR (V2.0.1)

V2.1.0 includes no IPRO6S applications or IPRO6S controller archives and does not support IPRO6S builds; for IPRO6S BR/EDR development (A2DP, AVRCP, HFP-HF, SCO), use V2.0.1. The following applies to V2.0.1.

In V2.0.1, IPRO6S shares the Zephyr 4.4 host and selects one of six dual-mode controllers, libipro_ble_controller_ipro6s_link{1,2,4}_br[_release].a. Start from V2.0.1's apps/platform/ipro6_btdm_phyrf/.config: CONFIG_IPRO6=y, CONFIG_BTDM_ENABLE=y, CONFIG_BTDM_BT_ENABLE=y and CONFIG_BTDM_MAX_ACL_CONNECTIONS=4. It demonstrates A2DP sink (SBC), AVRCP, HFP-HF and SCO audio over I2S and builds in V2.0.1 with:

./build_freertos.sh ipro6_btdm_phyrf build
Initialize the controller and HCI driver before calling bt_enable(). See the initialization example in Tutorials.

API Patterns

Applications use Zephyr-style callback-based BLE APIs. The legacy RivieraWaves ke_msg message passing mechanism is internal to the controller only and is not exposed to applications.

GAP: Advertising and Scanning

GAP Advertising Operations 
#include <zephyr/bluetooth/bluetooth.h>
#include <zephyr/bluetooth/conn.h>

/* Advertising data */
static const struct bt_data ad[] = {
    BT_DATA_BYTES(BT_DATA_FLAGS,
                  BT_LE_AD_GENERAL | BT_LE_AD_NO_BREDR),
    BT_DATA_BYTES(BT_DATA_UUID16_ALL,
                  0x0d, 0x18),  /* Heart Rate Service */
};

static const struct bt_data sd[] = {
    BT_DATA(BT_DATA_NAME_COMPLETE, "IPRO Device", 11),
};

/* Start connectable advertising */
bt_le_adv_start(BT_LE_ADV_CONN_NAME,
                ad, ARRAY_SIZE(ad), sd, ARRAY_SIZE(sd));

/* Stop advertising */
bt_le_adv_stop();

/* Start scanning (Central role) */
bt_le_scan_start(BT_LE_SCAN_ACTIVE, scan_cb);

Connection Callbacks

Connection Management 
static void connected(struct bt_conn *conn, uint8_t err)
{
    if (err) {
        printk("Connection failed (err %u)\n", err);
        return;
    }
    printk("Connected\n");
}

static void disconnected(struct bt_conn *conn, uint8_t reason)
{
    printk("Disconnected (reason %u)\n", reason);
}

static struct bt_conn_cb conn_callbacks = {
    .connected = connected,
    .disconnected = disconnected,
};

void app_init(void)
{
    bt_conn_cb_register(&conn_callbacks);
    bt_enable(bt_ready);
}

GATT: Service Registration

Static GATT Service Definition 
#include <zephyr/bluetooth/gatt.h>
#include <zephyr/bluetooth/uuid.h>

/* Custom UUIDs */
static struct bt_uuid_128 my_svc_uuid = BT_UUID_INIT_128(
    0xf0, 0xde, 0xbc, 0x9a, 0x78, 0x56, 0x34, 0x12,
    0x78, 0x56, 0x34, 0x12, 0x78, 0x56, 0x34, 0x12);

static struct bt_uuid_128 my_char_uuid = BT_UUID_INIT_128(
    0xf1, 0xde, 0xbc, 0x9a, 0x78, 0x56, 0x34, 0x12,
    0x78, 0x56, 0x34, 0x12, 0x78, 0x56, 0x34, 0x12);

static uint8_t my_value[256];

/* Read callback */
static ssize_t read_my_char(struct bt_conn *conn,
                            const struct bt_gatt_attr *attr,
                            void *buf, uint16_t len, uint16_t offset)
{
    return bt_gatt_attr_read(conn, attr, buf, len, offset,
                             my_value, sizeof(my_value));
}

/* Define service using macro (compile-time static registration) */
BT_GATT_SERVICE_DEFINE(my_svc,
    BT_GATT_PRIMARY_SERVICE(&my_svc_uuid),
    BT_GATT_CHARACTERISTIC(&my_char_uuid.uuid,
                           BT_GATT_CHRC_READ | BT_GATT_CHRC_NOTIFY,
                           BT_GATT_PERM_READ,
                           read_my_char, NULL, my_value),
    BT_GATT_CCC(NULL, BT_GATT_PERM_READ | BT_GATT_PERM_WRITE),
);

/* Send GATT notification */
bt_gatt_notify(conn, &my_svc.attrs[1], my_value, sizeof(my_value));
Note: The legacy RivieraWaves ke_msg API is deprecated. ipro_ble_controller.h remains the current controller bring-up API — ipro_ble_ctlr_controller_init() is still used alongside the Zephyr bt_* host APIs (see the API Reference). All new application host-layer code should use the Zephyr bt_* APIs.

LE Audio Ecosystem

LE Audio requires CONFIG_IPRO_BLE_CTLR_FEATURE="bt54_iso2". Headers are under ipro_bt_host/upstream/zephyr/include/zephyr/bluetooth/audio/.

LE Audio Profiles

Profile Full Name Function
BAP Basic Audio Profile Audio stream management (unicast/broadcast)
CAP Common Audio Profile Coordinated audio operations across device sets
VCP Volume Control Profile Volume control
MCP Media Control Profile Media playback control
CSIP Coordinated Set Identification Profile Coordinated device identification (e.g., left/right earbud pairing)

LC3 Codec Pipeline

LE Audio uses LC3 (Low Complexity Communication Codec) as its mandatory codec, with bitrate and latency determined by the negotiated codec preset, transport and application buffers. Audio data is transported over Isochronous Channels (CIS/BIS).

PAwR and ESL Availability

V2.1.0 host headers expose periodic advertising interfaces, but the release includes neither complete PAwR/ESL applications nor a dedicated _pawr controller archive. Header declarations and configuration options alone do not establish controller support.

For evaluation, obtain the matching controller, host configuration and test firmware from INTELPRO, then integrate against this release’s zephyr/bluetooth/bluetooth.h. For ordinary BLE applications, retain the controller combination supplied with the example.

BLE Low-Power Validation

Start with shipped configurations: ipro_ble_remote uses link1_periph / bt52; ipro_pdm_mic_demo uses link2 / bt52 with a one-connection host. Both use 16 KB EM. bt54_iso2 needs at least 32 KB EM and cannot reuse the same 16 KB retention configuration.

For general sleep testing, start with apps/test/ipro_lp_test/ and its pds command and board configuration. Record the board, measurement point, wake source, advertising/connection state and active peripherals. Measure current and wake latency for that setup.

Before sleeping, coordinate DMA, audio, timers and pending flash writes. Verify OCRAM/PSRAM retention and peripheral restoration for the selected mode. Persist bonding data through the Settings backend; RAM retention does not replace persistent storage.

Zephyr RTOS has no low-power modes yet (no PDS/HBN through pm_state, and the BLE controller does not sleep); use FreeRTOS for products that need low power.

App Framework

BLE applications use the Mediator design pattern, decomposing complex Bluetooth functionality into reusable components:

Component Role Description
Mediator Orchestrator Manages interactions and lifecycle of Applets, controls overall application flow
Applets Reusable components Encapsulate specific functionality (e.g., advertising management, GATT services, audio streams), shareable across applications
Intermediaries Protocol bridges Convert data formats between protocol layers, e.g., translating application-level commands into BLE GAP/GATT operations

This framework is primarily used in LE Audio applications (GAF, BAP, VCP, MCP, CAP) to modularize complex audio management logic.

Prebuilt Libraries

components/wireless/bluetooth/ipro_ble_controller/lib/

V2.1.0 ships IPRO7 controller archives only, 16 in total: link1_periph/link1/link2/link4 × bt52/bt54_iso2 × debug/release. The IPRO6S dual-mode controllers are available in V2.0.1 only.

The build selects an archive using LIB, FEATURE and CONFIG_IPRO_BLE_CTLR_CFG_DBG. The default is n, selecting a _release.a archive; y selects the archive without that suffix.

libipro_ble_controller_ipro7_link1_periph_bt54_iso2_release.a

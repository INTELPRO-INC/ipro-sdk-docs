Tutorial 1: Your First BLE Application

Learn how to create your first BLE application with IPRO SDK. This tutorial covers bt_enable() initialization, advertising setup, and connection callbacks.

Step 1: Project Structure

Each IPRO SDK application is a standalone directory under apps/<category>/<name>. We recommend copying apps/bluetooth/ble/ipro_ble_remote/ as a template and placing your project at the same level (e.g., apps/bluetooth/ble/my_ble_app/):

apps/bluetooth/ble/my_ble_app/
  .config            # Kconfig settings (CONFIG_BLUETOOTH_LE_ENABLE=y etc.)
  Makefile           # make entry point (contains PROJECT_NAME and IPRO_SDK_BASE)
  Kconfig            # Application-level Kconfig options
  CMakeLists.txt     # Build configuration
  main.c             # Application entry point

After copying the template, update PROJECT_NAME in Makefile and the project name passed to setup_project() in CMakeLists.txt. Adjust IPRO_SDK_BASE ?= $(abspath ../../../../) for the project’s directory depth.

Step 2: .config Settings

Enable BLE features in .config. Only the key settings are listed below; in practice, start from the .config of apps/bluetooth/ble/ipro_ble_remote/ and modify it:

# SoC and toolchain
CONFIG_IPRO7=y
CONFIG_CHIP="IPRO7"
CONFIG_CPU_ID="intelpro_ipro7"

# RTOS selection
CONFIG_FREERTOS_SUPPORT=y

# BLE Host + controller variant (prebuilt linkN library)
CONFIG_BLUETOOTH_LE_ENABLE=y
CONFIG_BT_CTLR_IPRO=y
CONFIG_BT_HOST_IPRO_V44=y
CONFIG_IPRO_BLE_CTLR_LIB="link1"
CONFIG_IPRO_BLE_CTLR_FEATURE="bt52"
CONFIG_IPRO_BLE_CTLR_CFG_DBG=n
CONFIG_BT_CONN=1
CONFIG_EM_SIZE=32

# NVDS: controller configuration storage; host bonds use BT_SETTINGS
CONFIG_ENABLE_NVDS=y
CONFIG_CFG_NVDS=y

# Shell CLI (for debugging, optional)
CONFIG_SHELL=y

Step 3: Initialize the Platform and BLE Controller

All FreeRTOS applications share the components/os/freertos/freertos_app_hooks.{c,h} component, which provides weak default implementations of the heap, FreeRTOS hooks, and platform initialization. A minimal main.c only needs to call ipro_platform_init() -- there is no need to hand-write any hooks or heap setup:

#include <stdio.h>
#include <FreeRTOS.h>
#include <task.h>
#include "ipro_ble_controller.h"          // ipro_ble_ctlr_controller_init()
#include "freertos_app_hooks.h"   // ipro_platform_init()

static void app_task(void *arg);  // Application main loop (see Step 4)

int main(void)
{
    // 1. Platform init (heap + boot2 + log + shell, provided by freertos_app_hooks)
    ipro_platform_init();

    // BLE initialization runs in app_task after scheduler startup.

    // 2. Create the application task
    xTaskCreate(app_task, "app", 2048, NULL, 3, NULL);

    // 3. Start the FreeRTOS scheduler
    vTaskStartScheduler();
    return 0;
}

To customize a hook (e.g., vApplicationIdleHook), simply define a non-weak version inside your application -- the linker picks it up automatically. Do not copy hooks/heap boilerplate back into main.c.

Step 4: Enable the BLE Host and Set Up Advertising

In your application task, call hci_driver_ipro_ble_ctlr_init() followed by bt_enable() (the order is fixed: ipro_ble_ctlr_controller_init → hci_driver_ipro_ble_ctlr_init → bt_enable), then start advertising in the ready callback:

#include <zephyr/bluetooth/bluetooth.h>
#include <zephyr/bluetooth/conn.h>
#include <hci_driver_ipro_ble_ctlr.h>

static const struct bt_data ad[] = {
    BT_DATA_BYTES(BT_DATA_FLAGS,
                  BT_LE_AD_GENERAL | BT_LE_AD_NO_BREDR),
    BT_DATA_BYTES(BT_DATA_NAME_COMPLETE, 'I','P','R','O'),
};

static void bt_ready(int err)
{
    if (err) {
        printf("BLE init failed (err %d)\n", err);
        return;
    }
    // Start advertising
    err = bt_le_adv_start(BT_LE_ADV_CONN_FAST_1, ad, ARRAY_SIZE(ad),
                          NULL, 0);
    if (err) {
        printf("Advertising failed (err %d)\n", err);
    }
}

static void app_task(void *arg)
{
    // The HCI driver must be initialized before bt_enable()
    int err = ipro_ble_ctlr_controller_init(configMAX_PRIORITIES - 1);
    if (err) {
        printf("Controller init failed (err %d)\n", err);
        vTaskDelete(NULL);
        return;
    }
    vTaskDelay(pdMS_TO_TICKS(50));
    err = hci_driver_ipro_ble_ctlr_init();
    if (err) {
        printf("HCI driver init failed (err %d)\n", err);
        vTaskDelete(NULL);
        return;
    }

    vTaskDelay(pdMS_TO_TICKS(50));
    err = bt_enable(bt_ready);
    if (err) {
        printf("bt_enable failed (err %d)\n", err);
    }

    for (;;) {
        vTaskDelay(portMAX_DELAY);
    }
}

Step 5: Connection Callbacks

Define a struct bt_conn_cb and register it with bt_conn_cb_register() (recommended at the beginning of bt_ready()):

static void connected(struct bt_conn *conn, uint8_t err)
{
    if (err) {
        printf("Connection failed (err 0x%02x)\n", err);
        return;
    }
    printf("Connected\n");
}

static void disconnected(struct bt_conn *conn, uint8_t reason)
{
    printf("Disconnected (reason 0x%02x)\n", reason);
    // Restart advertising
    bt_le_adv_start(BT_LE_ADV_CONN_FAST_1, ad, ARRAY_SIZE(ad),
                    NULL, 0);
}

static struct bt_conn_cb conn_callbacks = {
    .connected = connected,
    .disconnected = disconnected,
};

// Register inside bt_ready():
//     bt_conn_cb_register(&conn_callbacks);

Step 6: Build and Flash

# Build (the output binary carries the _IPRO7 chip suffix)
make -C apps/bluetooth/ble/my_ble_app
# → apps/bluetooth/ble/my_ble_app/build/build_out/my_ble_app_IPRO7.bin

# Flash (serial port name depends on your device)
/path/to/ipro_iot_tool_lite \
    --chipname ipro7 \
    --port /dev/cu.usbserial-XXXX \
    --firmware apps/bluetooth/ble/my_ble_app/build/build_out/my_ble_app_IPRO7.bin \
    --baudrate 921600 --flash-pin 0x02

# Or use build_freertos.sh to build + flash + monitor in one step
./build_freertos.sh my_ble_app build flash monitor

Reference Example

For a complete BLE application example, see apps/bluetooth/ble/ipro_ble_remote/, which includes LED control, button detection, environment sensing, UART bridge, and OTA upgrade features.

Tutorial 2: Build & Flash Workflow

Master the IPRO SDK build system and firmware flashing workflow.

Build Methods

IPRO SDK provides two build methods:

# Method 1: Using build_freertos.sh (recommended, supports chained actions)
./build_freertos.sh ipro_ble_remote build

# Chain actions: build + flash + open serial monitor
./build_freertos.sh ipro_ble_remote build flash monitor

# Other actions: clean / size (ELF size + memory region usage report)
./build_freertos.sh clean build bluetooth/ble/ipro_ble_remote
./build_freertos.sh size bluetooth/ble/ipro_ble_remote

# List all buildable projects
./build_freertos.sh -l

# Method 2: Using Make (low-level, requires the full nested path apps/<category>/<name>)
make -C apps/bluetooth/ble/ipro_ble_remote

# Clean build
make -C apps/bluetooth/ble/ipro_ble_remote clean

Common build_freertos.sh options: -p to specify the serial port, -t to set the timeout in seconds, and -w to set the output pattern (regex) the monitor waits for. Build output is located at apps/<category>/<name>/build/build_out/. Binary names include a chip suffix, e.g., ipro_ble_remote_IPRO7.bin.

.config Settings

Each application has its own .config file using Linux Kernel Kconfig format. Taking a BLE application as an example:

# SoC selection
CONFIG_IPRO7=y
CONFIG_CHIP="IPRO7"
CONFIG_CPU_ID="intelpro_ipro7"

# RTOS selection
CONFIG_FREERTOS_SUPPORT=y

# BLE features and controller variant
CONFIG_BLUETOOTH_LE_ENABLE=y
CONFIG_BT_CTLR_IPRO=y
CONFIG_BT_HOST_IPRO_V44=y
CONFIG_IPRO_BLE_CTLR_LIB="link1"
CONFIG_IPRO_BLE_CTLR_FEATURE="bt52"
CONFIG_IPRO_BLE_CTLR_CFG_DBG=n
CONFIG_BT_CONN=1
CONFIG_EM_SIZE=32

# NVDS: controller configuration storage; host bonds use BT_SETTINGS
CONFIG_ENABLE_NVDS=y
CONFIG_CFG_NVDS=y

# Shell CLI
CONFIG_SHELL=y

Flash Firmware

Use the separately installed flash tool ipro_iot_tool_lite (the serial port name depends on your device; on macOS, find it with ls /dev/cu.usbserial-*):

# Basic flash command
/path/to/ipro_iot_tool_lite \
    --chipname ipro7 \
    --port /dev/cu.usbserial-XXXX \
    --firmware apps/bluetooth/ble/ipro_ble_remote/build/build_out/ipro_ble_remote_IPRO7.bin \
    --baudrate 921600 \
    --flash-pin 0x02

macOS Serial Port Notes

On macOS, you must use /dev/cu.* instead of /dev/tty.*. The tty.* devices block waiting for the DCD signal and will not work.

Serial Monitor

V2.0.1 omits the old monitor helper. Install pyserial and open its terminal:

# Install separately; select the port and baud rate for your firmware
python3 -m pip install pyserial
python3 -m serial.tools.miniterm /dev/cu.usbserial-XXXX 115200

Automated Workflow (Separate Helpers Required)

build_freertos.sh can chain build, flash, and monitor into a single command. Combine it with -w/-t to wait for expected output, which makes it easy to integrate into automation scripts:

# One line: build + flash + monitor
./build_freertos.sh ipro_ble_remote build flash monitor

# Wait for the application boot output (60-second timeout)
./build_freertos.sh -w "BLE 5.4 stack initialized" -t 60 \
    ipro_ble_remote build flash monitor

Tutorial 3: BLE Throughput Testing

Use the ipro_throughput_test application to measure BLE data throughput, achieving up to 999 Kbps on 2M PHY.

Overview

The throughput test runs between two IPRO7 development boards -- one as Slave (Peripheral) and the other as Master (Central). The application uses native Zephyr bt_* APIs.

Step 1: Build and Flash

Flash the same firmware to both development boards (the two boards have different serial port names; adjust to your actual devices):

# Build throughput test application
make -C apps/bluetooth/ble/ipro_throughput_test

# Flash to both boards
/path/to/ipro_iot_tool_lite \
    --chipname ipro7 --port /dev/cu.usbserial-XXXX \
    --firmware apps/bluetooth/ble/ipro_throughput_test/build/build_out/ipro_throughput_test_IPRO7.bin \
    --baudrate 921600 --flash-pin 0x02

Step 2: Start Test

# On the Slave board:
tp slave

# On the Master board (auto-scan and connect):
tp master

# Or specify MAC address:
tp master XX:XX:XX:XX:XX:XX

Step 3: Run Throughput Test

# After connection, switch to 2M PHY first (required to reach 999 Kbps)
tp phy 2

# Start test (default 200 bytes/packet, 10 seconds)
tp start

# Custom packet size and duration (use 244 bytes for maximum throughput)
tp start 244 10    # 244 bytes, 10 seconds

# View real-time statistics
tp stats

# Stop test
tp stop

Other tuning commands: tp phy <1|2|3> switches PHY (1=1M, 2=2M, 3=Coded), tp conn <min> <max> updates the connection interval (units of 1.25ms), and tp interval <ms> changes the TX interval.

Performance Optimization

IPRO SDK achieves 999 Kbps throughput through the following optimizations:

  • Connection parameter tuning: Minimum connection interval, zero Slave Latency
  • MTU negotiation: Maximum MTU to reduce per-packet overhead
  • TX Descriptor optimization: BLE_NB_TX_DESC_PER_CON parameter tuning
  • DLE (Data Length Extension): Enable maximum transmission length
  • 2M PHY: Use BLE 2M PHY for faster data rate

Measured reference numbers (244 bytes/packet):

PHYConnection IntervalThroughput
1M7.5 ms507 Kbps
2M7.5 ms999 Kbps
2M15 ms984 Kbps

Expected Results

During the test, a real-time statistics line is printed every second, and tp stats shows the cumulative results (the numbers below are illustrative; actual values depend on PHY and connection parameters):

[TP] TX: 512 pkts, 124928 bytes, 998.4 Kbps | RX: 0 pkts, 0 bytes, 0.0 Kbps | Err: 0

TX: 5016 packets, 1223904 bytes, 999.15 Kbps (124.89 KBps)
RX: 0 packets, 0 bytes, 0.00 Kbps (0.00 KBps)

Reference

For the complete operation manual, see apps/bluetooth/ble/ipro_throughput_test/README.md.

Tutorial 4: LE Audio Getting Started

Understand the core concepts of BLE 5.4 LE Audio, including BAP/BIS architecture, and how to use IPRO SDK's LE Audio example applications.

LE Audio Core Concepts

  • BAP (Basic Audio Profile): Defines audio stream establishment and management
  • CIS (Connected Isochronous Stream): Point-to-point audio, used for headsets
  • BIS (Broadcast Isochronous Stream): One-to-many broadcast audio, used for Auracast
  • LC3 Codec: LE Audio standard codec, low latency and high quality
  • GAF (Generic Audio Framework): Unified audio framework integrating BAP, VCP, MCP, CAP profiles

Controller Variant Selection

LIBACLRoles
link1_periph1Peripheral
link11Central + Peripheral
link22Central + Peripheral
link44Central + Peripheral

Choose CONFIG_IPRO_BLE_CTLR_FEATURE="bt52" for basic BLE or "bt54_iso2" for BLE 5.4 with two ISO streams (CIS/BIS). The latter requires CONFIG_EM_SIZE of at least 32 KB. Keep the host connection limit within controller capacity; preserve each shipped application configuration.

BIS Broadcast Examples

Standalone ipro_le_audio_bis_source and ipro_le_audio_bis_sink applications are not included in V2.0.1. The host includes broadcast APIs; contact INTELPRO for complete broadcast reference applications.

BLE Development Guide

This guide covers BLE application development with the IPRO SDK's Bluetooth stack. The SDK uses the Zephyr BLE Host Stack paired with a RivieraWaves prebuilt controller, providing full BLE 5.4 support.

Zephyr BLE Host Architecture

The IPRO SDK's operating system is FreeRTOS — Zephyr's role in the SDK is as the source of the BLE Host protocol stack, not as the RTOS kernel. components/wireless/bluetooth/blestack/ is ported from the Zephyr BLE Host (GAP, GATT, L2CAP, SMP, ISO, LE Audio) and runs on top of FreeRTOS via the port/ layer. Applications always develop against the Zephyr-style bt_* APIs.

  • Host — buildable source: blestack/ is ported from Zephyr; full source ships with the SDK and can be read and debugged directly
  • Controller — prebuilt static libraries: the RivieraWaves controller ships as prebuilt linkN variant libraries, 13 variants in total: link1_periph, link1, link1_53, link1_54, link2, link2_54, link4, link8, link1_leaudio, link2_leaudio, link1_leaudio_53_54, link2_leaudio_53_54, link4_leaudio_53_54
  • RTOS — FreeRTOS: scheduling, queues, and timers are all provided by FreeRTOS; the Zephyr kernel is not present in the system
Further reading: the complete BLE Host Architecture Guide is not included in the release package — contact the vendor to obtain it.

Stack Architecture

The BLE stack uses a Host + Controller dual-layer architecture, communicating through on-chip HCI (no UART HCI transport):

Application Layer
GAP / GATT Services / Profiles
BLE Host (Zephyr-based)
GAP / GATT / L2CAP / SMP / ISO
HCI (On-Chip)
ipro_hci_wrapper
BLE Controller (RivieraWaves)
Link Layer / PHY (1M/2M/Coded)

Core Concepts

  • Zephyr BLE Host: The Zephyr BLE Host Stack is used even on FreeRTOS. Applications interact through the standard bt_* APIs
  • RivieraWaves Controller: Provided as prebuilt static libraries, handling Link Layer and PHY management
  • On-Chip HCI: Host and Controller communicate via on-chip HCI, no UART HCI transport layer required
  • Callback-driven: All asynchronous events (connection, disconnection, notifications) are handled through callback functions

Kconfig Configuration

Select the controller variant in your application's .config by specifying the full variant name in CONFIG_BTBLECONTROLLER_LIB (recommended — consistent with every reference application in the SDK):

.config Variant Selection 
# Specify the full variant name directly (recommended)
CONFIG_BTBLECONTROLLER_LIB="link2_leaudio_53_54"

# Or use boolean flag composition (suffixes appended automatically)
CONFIG_BTBLECONTROLLER_LIB="link2"
CONFIG_BTBLECONTROLLER_LE_AUDIO=y     # Appends _leaudio
CONFIG_BTBLECONTROLLER_BT_53=y        # Appends _53
CONFIG_BTBLECONTROLLER_BT_54=y        # Appends _54
# Resulting variant: link2_leaudio_53_54
Note: the result of flag composition must map to a prebuilt library directory that actually exists. LE Audio variants are only provided as _leaudio_53_54 libraries — raw .config builds do not resolve Kconfig select, so both CONFIG_BTBLECONTROLLER_BT_53=y and CONFIG_BTBLECONTROLLER_BT_54=y must be set explicitly. Base variants (without LE Audio) have no _53_54 combination (the existing libraries are link1_53, link1_54, and link2_54) — set only one of the two flags; setting both composes a nonexistent directory and the link stage fails. Specifying the full name directly in CONFIG_BTBLECONTROLLER_LIB avoids this pitfall.
NVDS must be enabled: flash-based BLE applications must set CONFIG_ENABLE_NVDS=y and CONFIG_CFG_NVDS=y in .config, otherwise the controller link stage fails with undefined symbols such as __nvds_start.

Prebuilt libraries are located at: components/wireless/bluetooth/btblecontroller_ipro7_<variant>/

API Patterns

Applications use Zephyr-style callback-based BLE APIs. The legacy RivieraWaves ke_msg message passing mechanism is internal to the controller only and is not exposed to applications.

GAP: Advertising and Scanning

GAP Advertising Operations 
#include <bluetooth/bluetooth.h>
#include <bluetooth/conn.h>

/* Advertising data */
static const struct bt_data ad[] = {
    BT_DATA_BYTES(BT_DATA_FLAGS,
                  BT_LE_AD_GENERAL | BT_LE_AD_NO_BREDR),
    BT_DATA_BYTES(BT_DATA_UUID16_ALL,
                  0x0d, 0x18),  /* Heart Rate Service */
};

static const struct bt_data sd[] = {
    BT_DATA(BT_DATA_NAME_COMPLETE, "IPRO Device", 11),
};

/* Start connectable advertising */
bt_le_adv_start(BT_LE_ADV_CONN_NAME,
                ad, ARRAY_SIZE(ad), sd, ARRAY_SIZE(sd));

/* Stop advertising */
bt_le_adv_stop();

/* Start scanning (Central role) */
bt_le_scan_start(BT_LE_SCAN_ACTIVE, scan_cb);

Connection Callbacks

Connection Management 
static void connected(struct bt_conn *conn, u8_t err)
{
    if (err) {
        printk("Connection failed (err %u)\n", err);
        return;
    }
    printk("Connected\n");
}

static void disconnected(struct bt_conn *conn, u8_t reason)
{
    printk("Disconnected (reason %u)\n", reason);
}

static struct bt_conn_cb conn_callbacks = {
    .connected = connected,
    .disconnected = disconnected,
};

void app_init(void)
{
    bt_conn_cb_register(&conn_callbacks);
    bt_enable(bt_ready);
}

GATT: Service Registration

Static GATT Service Definition 
#include <bluetooth/gatt.h>
#include <bluetooth/uuid.h>

/* Custom UUIDs */
static struct bt_uuid_128 my_svc_uuid = BT_UUID_INIT_128(
    0xf0, 0xde, 0xbc, 0x9a, 0x78, 0x56, 0x34, 0x12,
    0x78, 0x56, 0x34, 0x12, 0x78, 0x56, 0x34, 0x12);

static struct bt_uuid_128 my_char_uuid = BT_UUID_INIT_128(
    0xf1, 0xde, 0xbc, 0x9a, 0x78, 0x56, 0x34, 0x12,
    0x78, 0x56, 0x34, 0x12, 0x78, 0x56, 0x34, 0x12);

static uint8_t my_value[256];

/* Read callback */
static ssize_t read_my_char(struct bt_conn *conn,
                            const struct bt_gatt_attr *attr,
                            void *buf, u16_t len, u16_t offset)
{
    return bt_gatt_attr_read(conn, attr, buf, len, offset,
                             my_value, sizeof(my_value));
}

/* Define service using macro (compile-time static registration) */
BT_GATT_SERVICE_DEFINE(my_svc,
    BT_GATT_PRIMARY_SERVICE(&my_svc_uuid),
    BT_GATT_CHARACTERISTIC(&my_char_uuid.uuid,
                           BT_GATT_CHRC_READ | BT_GATT_CHRC_NOTIFY,
                           BT_GATT_PERM_READ,
                           read_my_char, NULL, my_value),
    BT_GATT_CCC(NULL, BT_GATT_PERM_READ | BT_GATT_PERM_WRITE),
);

/* Send GATT notification */
bt_gatt_notify(conn, &my_svc.attrs[1], my_value, sizeof(my_value));
Note: The legacy RivieraWaves ke_msg API is deprecated. ble_lib_api.h remains the current controller bring-up API — ble_controller_init() is still used alongside the Zephyr bt_* host APIs (see the API Reference). All new application host-layer code should use the Zephyr bt_* APIs.

LE Audio Ecosystem

The SDK supports comprehensive LE Audio functionality, requiring controller variants with the _leaudio suffix. Headers are located at bluetooth/audio/.

LC3 Codec Pipeline

LE Audio uses LC3 (Low Complexity Communication Codec) as its mandatory codec, supporting 32-320 kbps bitrates with audio latency below 20ms. Audio data is transported over Isochronous Channels (CIS/BIS).

Configuration Example

PAwR & ESL

BLE 5.4 introduces PAwR (Periodic Advertising with Responses), letting a broadcaster collect responses from observers in fixed subevent slots without establishing one-to-one connections. The SDK supports PAwR in both host and controller layers — it is the foundation of IPRO's large-scale sensor and ESL applications.

Typical Architecture

  • Gateway / Broadcaster: broadcasts a PAwR train every PA interval, containing multiple subevents. Subevent 0 is typically the provisioning channel; subevents 1+ are assigned to paired sensors.
  • Sensor / Observer: wakes up only in its assigned subevent slot, parses the broadcaster command, returns sensor data, and goes back to deep sleep.
  • Connectionless: the sensor count can far exceed controller link limits (typical 32 sensors per interval).

Key API

PAwR Host API 
/* ── Broadcaster (gateway side) ─────────────────────────── */
/* 1. Create an ext adv set with PAwR callbacks attached */
static const struct bt_le_ext_adv_cb adv_cb = {
    .pawr_data_request = pawr_data_request_cb,  /* controller asks for subevent data */
    .pawr_response     = pawr_response_cb,      /* response received from an observer */
};
bt_le_ext_adv_create(&adv_param, &adv_cb, &adv);

/* 2. Configure the PAwR train parameters and start */
struct bt_le_per_adv_param per_param = {
    .interval_min          = 800,   /* N * 1.25 ms = 1 s */
    .interval_max          = 800,
    .num_subevents         = 32,
    .subevent_interval     = 24,    /* N * 1.25 ms = 30 ms */
    .response_slot_delay   = 12,    /* N * 1.25 ms = 15 ms */
    .response_slot_spacing = 8,     /* N * 0.125 ms = 1 ms */
    .num_response_slots    = 4,
};
bt_le_per_adv_set_param(adv, &per_param);
bt_le_per_adv_start(adv);

/* 3. Provide per-subevent data inside the pawr_data_request callback */
bt_le_per_adv_set_subevent_data(adv, num_subevents, subevent_params);

/* ── Observer (sensor / tag side) ───────────────────────── */
/* 1. Register PA sync and PAwR data callbacks, scan, then create the PA sync */
bt_le_pa_sync_cb_register(pa_sync_established);
bt_le_pa_sync_lost_cb_register(pa_sync_lost);
bt_le_pa_pawr_data_cb_register(pawr_data_received);
bt_le_scan_start(&scan_param, scan_cb);
/* After the broadcaster is found, sync is created with the
 * HCI LE Periodic Advertising Create Sync command; the sync
 * handle is delivered via the pa_sync_established callback */

/* 2. After sync is established: subscribe to the subevents to listen on */
struct bt_le_per_adv_sync_subevent_params se_params = {
    .num_subevents = 1,
    .subevents     = my_subevents,
};
bt_le_per_adv_sync_subevent(sync_handle, &se_params);

/* 3. Return data in a response slot inside the pawr_data_received callback */
struct bt_le_per_adv_response_params rsp_params = {
    .request_event     = periodic_event_counter,
    .request_subevent  = subevent,
    .response_subevent = subevent,
    .response_slot     = 0,
};
bt_le_per_adv_set_response_data(sync_handle, &rsp_params, &rsp_buf);
Note: subevent_interval must leave the host enough data-preparation headroom — with too short an interval, the host cannot deliver data before the next round of subevents. If the subevent payload requires extra processing (e.g., encryption), widen the interval further.

ESL (Electronic Shelf Label)

The host and controller provide the BLE 5.4 capabilities required by the SIG ESL Profile:

  • PAwR subevent provisioning: subevent 0 serves as the provisioning channel; subevents 1+ are assigned to paired tags
  • PAST (Periodic Advertising Sync Transfer): bt_le_per_adv_sync_transfer() / bt_le_per_adv_sync_transfer_subscribe() / bt_le_per_adv_sync_transfer_unsubscribe() — the AP can hand off an established PA sync while the GATT link is up, eliminating the tag's post-provisioning scan window
  • Shared protocol definitions: components/wireless/bluetooth/include/esl_defs.h — opcodes aligned with SIG ESL Profile v1.0.1 (incl. READ_SENSOR 0x10) plus PAwR packet structures

Complete ESL turnkey reference designs (tag + gateway) are available from the vendor on request.

Low Power BLE

IPRO7 supports multiple low-power tiers; BLE applications can enter PDS (Power Down Sleep) between advertising / connection events to reach µA-level average current.

PDS Level 31 — Deep Sleep

  • Full OCRAM retention: all 256 KB of OCRAM banks are retained by default — no PDS_RAM_Config() call required.
  • BLE Exchange Memory: lives at the top of OCRAM (0x1104_0000~), outside the retention partition.
  • BZ Controller: with pdsCtl4.BzRst=1, BzGateClk=1 the PDS resets and gates the BLE controller clock during sleep; the controller is re-initialized on wakeup.
  • Automatic RF shutdown: pdsCtlRfSel=1 in hal_pm.c lets the PDS hardware shut down RF analog blocks during sleep, dropping current from 80 µA to ~10 µA.
  • turnoffDLL=0: under cpuRst=1 the post-WFI path skips the DLL re-initialization sequence.

Cold Boot with Detection

Hardware testing has shown that cpuRst=0 (pure WFI resume) is not viable in BLE controller mode. The verified approach is cpuRst=1 + RSV0=0 + RSV2=flag, detecting the wakeup cause during cold boot and jumping back to BLE state after bootrom. Wakeup latency is roughly 100 ms — suitable for sparse wakeup cycles; maintaining live BLE connections still requires sleep clock calibration.

Low-Power BLE Application Patterns

  • PDS31 verification app (ipro_ble_lowpower_test) — covers RF reinit, register save/restore, and sleep margin measurement; PDS31 entry/exit is hardware-verified. This app is a capability demonstration not included in the release — contact the vendor to obtain it.
  • PAwR sensor tag — the observer wakes only for its assigned subevent and returns to deep sleep immediately after responding (see the PAwR & ESL section).
  • Sensor-triggered wakeup — wake on an external sensor interrupt, with application data retained in PSRAM across sleep cycles; suited to event-driven products. Turnkey reference designs are available from the vendor.
Tip: Before tweaking LP/PDS configuration, rule out application-level bugs first. Most "current went up" reports are tasks failing to enter idle or timers not being released, not the LP settings themselves.

App Framework

BLE applications use the Mediator design pattern, decomposing complex Bluetooth functionality into reusable components:

Component Role Description
Mediator Orchestrator Manages interactions and lifecycle of Applets, controls overall application flow
Applets Reusable components Encapsulate specific functionality (e.g., advertising management, GATT services, audio streams), shareable across applications
Intermediaries Protocol bridges Convert data formats between protocol layers, e.g., translating application-level commands into BLE GAP/GATT operations

This framework is primarily used in LE Audio applications (GAF, BAP, VCP, MCP, CAP) to modularize complex audio management logic.

Prebuilt Libraries

The BLE controller is always provided as prebuilt static libraries (.a), each accompanied by .a.version version metadata. Applications only need to specify the variant name in .config (see Controller Variants); the build system links the matching library automatically — no extra build step is required.

Important: the release package does not include controller source, and CONFIG_BLE_FORCE_SOURCE_BUILD is not supported. For custom controller variants (link count, feature combinations), contact the vendor.
